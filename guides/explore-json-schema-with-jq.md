# Explore the JSON Schema with jq

Use this page to answer common questions about a feature type by querying its JSON
Schema with [`jq`](https://jqlang.org/), a small command-line tool for querying JSON. You
can generate the JSON Schema for any feature type with the Overture schema packages. If you'd
rather use Python, load the file with `json.load()` and use the same paths as dictionary
keys.

## Before you start

You need the `overture-schema` command, installed in a virtual environment, and `jq`:

```bash
pip install overture-schema
brew install jq
```

On Linux, install `jq` with your package manager, for example `apt install jq`.

Generate the JSON Schema for one feature type and save it, so you don't have to rerun the
command for every query:

```bash
overture-schema json-schema --type building > building.schema.json
```

The file is about 700 lines.

## Find a field

The JSON Schema describes a feature in its GeoJSON form. `id` and `geometry` are at the
top level, and the other fields are inside `properties`. So most fields are three levels
down:

```bash
jq '.properties.properties.properties | keys' building.schema.json
```
```json
["class","facade_color","facade_material","has_parts","height","is_underground",
 "level","min_floor","min_height","names","num_floors","num_floors_underground",
 "roof_color","roof_direction","roof_height","roof_material","roof_orientation",
 "roof_shape","sources","subtype","theme","type","version"]
```

The word `properties` appears three times in that path, and each one means something
different:

| Path | Means |
|---|---|
| `.properties` | the fields of the document, a JSON Schema keyword |
| `.properties.properties` | the GeoJSON field named `properties` |
| `.properties.properties.properties` | the fields inside that one, the keyword again |

`id`, `geometry`, and `bbox` aren't in that list. They're at `.properties.id`,
`.properties.geometry`, and `.properties.bbox`, the same as in a GeoJSON feature.

You don't need to count levels. `jq` can find the path to any field:

```bash
jq -c 'paths | select(.[-1]=="height")' building.schema.json
```
```json
["properties","properties","properties","height"]
```

If a query returns `null`, check the path. `jq` returns `null` for a key that doesn't
exist instead of reporting an error, so a `null` usually means the path stops a level too
high.

## Look up one field's rules

```bash
jq '.properties.properties.properties.height' building.schema.json
```
```json
{
  "description": "Height of the building or part in meters.\n\nThis is the distance from the lowest point to the highest point.",
  "exclusiveMinimum": 0,
  "title": "Height",
  "type": "number"
}
```

That object isn't a value of `height`. In the data, `height` is a number such as
`443.2`. The object has the rules for `height`: it must be a number, and it must be
greater than zero.

Each keyword is generated from the field's declaration in the Python model:

| Schema keyword | Comes from |
|---|---|
| `"type": "number"` | the `float64` annotation |
| `"exclusiveMinimum": 0` | `gt=0`: greater than, not greater than or equal to |
| `"description"` | the `description=` argument |
| `"title": "Height"` | generated by Pydantic from the field name |

## List the valid values for a field

Enums and shared structures are defined once, at the top level under `$defs`:

```bash
jq -r '.["$defs"] | keys[]' building.schema.json
```
```
BuildingClass BuildingSubtype FacadeMaterial NameRule NameVariant Names
PerspectiveMode Perspectives RoofMaterial RoofOrientation RoofShape Side SourceItem
```

To list the values a field accepts, query its enum:

```bash
jq -r '.["$defs"].BuildingClass.enum[]' building.schema.json | head
```
```
agricultural
allotment_house
apartments
barn
beach_hut
boathouse
bridge_structure
bungalow
```

## Find the required fields

The GeoJSON envelope splits the required fields into two lists, one for each level:

```bash
jq '.required' building.schema.json
jq '.properties.properties.required' building.schema.json
```
```json
["type","id","geometry","properties"]
["theme","type","version"]
```

Read both. Together they name five Overture fields: `id` and `geometry` at the top level,
and `theme`, `type`, and `version` inside `properties`. `type` and `properties` in the
first list are GeoJSON keys. If you read only the second list, you miss `id` and
`geometry`.

Each nested structure, such as `Names` or `SourceItem`, has its own `required` list.

## Things the JSON Schema doesn't tell you

The rules for one field don't include:

- **Whether the field may be omitted.** That's in the `required` list of the object that
  contains it.
- **Units.** "In meters" is part of the `description`, which is text for people. Nothing
  rejects a height recorded in feet.
- **Rules between fields, unless the model declares one.** No rule ties `height` to
  `min_height`, for example.
